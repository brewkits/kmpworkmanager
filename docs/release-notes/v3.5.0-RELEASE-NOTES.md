# v3.5.0 — Hardening

**Type:** Minor release. No new features; 20 bug fixes, two of which change
observable behaviour (see below), plus documentation corrections and the removal
of every skipped test from the suite.

**Who should read the breaking section:** anyone using `KmpHeavyWorker` on
Android 15+, and anyone whose tests use `FakeBackgroundTaskScheduler`.

---

## Breaking / behaviour changes

### 1. `KmpHeavyWorker.FGS_MEDIA_PROCESSING` is now 8192, was 4096

`4096` was simply the wrong number. The platform constant
`ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PROCESSING` is `8192`; `4096` is not
any foreground-service type at all. The consequence on Android 15 was total:
every media-processing heavy worker threw `ForegroundServiceTypeException` and
retried forever.

The constant now reads from the platform rather than declaring its own literal,
so it cannot drift again.

**You are affected if** you hardcoded `4096` — in your manifest's
`android:foregroundServiceType`, or by copying the old constant's value — to match
what the library was sending. Remove the workaround and declare
`mediaProcessing` normally.

**Note on the declaration:** the constant is a `@JvmField val`, not a `const val`.
A `const` is inlined into *your* bytecode when *you* compile, so bumping the
library version without recompiling would have kept the old 4096. Reading a field
picks up the correct value immediately.

### 2. `FakeBackgroundTaskScheduler.isPending(id)` returns `false` after `cancelAll()`

`cancelAll()` sets a flag without touching `cancelledIds`, so `isPending(id)` used
to keep reporting `true` for every task after everything had been cancelled —
while `pendingTaskCount()`, answering the same question, correctly returned `0`.

**You are affected if** a test asserts `assertTrue(fake.isPending("x"))` after a
`cancelAll()`. It will now fail — correctly. It was passing on a wrong answer.

This module (`kmpworker-testing`) had no tests of its own until this release; its
first eight found this.

## Added

### TLS certificate pinning, opt-in

`HttpClientProvider.configurePinning(...)` pins one or more hosts to SHA-256 SubjectPublicKeyInfo
digests, in the `sha256/BASE64` form OkHttp and every pin-generating tool emit.

```kotlin
HttpClientProvider.configurePinning(
    listOf(
        CertificatePin(
            hostname = "api.example.com",
            sha256Pins = listOf(
                "sha256/AAAA…",  // current
                "sha256/BBBB…",  // backup — see below
            ),
        ),
    ),
)
```

**Opt-in, and that is load-bearing.** An app that never calls it gets the client it always had:
no challenge handler is installed on iOS and no `CertificatePinner` on Android. Pinning one host
leaves every other host on default validation.

Pinning is **additional to** the system's chain validation, never a replacement for it. On both
platforms a matching pin still results in the OS performing its own expiry, hostname and trust
store checks. The first iOS draft got this backwards — it evaluated the chain itself and then
supplied a credential, which is how a pin becomes a way to *accept* an expired certificate — and
it did not work either, rejecting valid chains outright.

> **Ship a backup pin.** This is the failure that makes teams abandon pinning and it cannot be
> fixed from the server: pin only the key in use today, rotate it, and every installed copy of
> the app loses the ability to reach you. `CertificatePin`'s KDoc says so at the point of use.

**On verification.** Android delegates to OkHttp's `CertificatePinner`, which does its own SPKI
hashing. iOS computes the digest here, because `SecKeyCopyExternalRepresentation` returns the raw
key while a `sha256/` pin covers the full SubjectPublicKeyInfo — the ASN.1 header has to be
reattached, and it differs per key type and size. That computation was verified against `openssl`
on a live server: for `www.example.com` (EC P-256) this code produced
`sha256/CFZ1L1MZmmc9zJVcE3/h9bEFoYBSissyC7Pt3xUQOps=`, character for character what
`openssl … | openssl dgst -sha256 | base64` produced for the same certificate, and a deliberately
wrong pin was rejected.

`TlsPinningNetworkTest` keeps that check runnable (`KMP_RUN_NETWORK_TESTS=1`). It first attempts
an **unpinned** request and skips with an explicit message if that fails, because a machine whose
trust store cannot validate any host would otherwise report "pinning is broken" — which is exactly
what happened on the machine this was developed on, where unpinned requests to apple.com,
cloudflare.com and example.com all failed.

## Fixed

Twenty bugs. The ones with the widest blast radius:

**Security**

- `SecurityValidator` allowed a trailing-dot FQDN (`localhost.`) straight through
  the SSRF blocklist — same host, no entry matched. Named hosts only; numeric
  literals were already rejected.
- The manual redirect interceptor never advanced its notion of the current
  request, so on hop ≥ 2 a relative `Location` resolved against the **original**
  host — a third-party redirect could aim an authenticated request at any path on
  your origin — and `Authorization`/`Cookie` stripped on an earlier cross-origin
  hop came back.
- `sanitizedURL` redacted the query string but not RFC 3986 UserInfo, so HTTP
  Basic credentials in a URL were logged verbatim — and, because that output is
  embedded in `WorkerResult` messages, persisted to the event store.
- `HttpUploadWorker` was the only HTTP worker not validating its file path, which
  a previous chain step could overwrite via `mergeOutputFromPreviousStep`.

**Data loss**

- `ExistingPolicy.KEEP` deleted the pending task's spilled input file before the
  enqueue decision was made, so the task that KEEP preserved ran with
  `input = null`. A regression introduced in v3.4.1.
- A chain step's input and its predecessor's output were each checked against 8 KB
  independently — but WorkManager merges them before the worker runs and caps the
  result at 10240 bytes. A legal pair met at ~16 KB and killed the chain inside
  `WorkerWrapper`, before any worker code could report it. Chain steps now share a
  budget.
- iOS: `crashAttemptCount` was incremented on every chain invocation and reset
  nowhere, so any chain long enough to span five BGTask windows was quarantined as
  a "poison pill" and deleted along with every step it had completed.
- iOS: a cancellation during `executeChain`'s prologue lost the chain outright —
  already off the queue, not yet running, definition still on disk with nothing to
  pick it up. BGTask expiry there is how a background window normally ends.
- Both event stores' low-disk guard returned a freshly minted event id after
  writing nothing, so a silent data loss was logged as a successful save.
- HTTP 416 promoted a resumed partial to its final path without verifying the
  checksum — precisely when the bytes are least trustworthy.

**Correctness**

- Retry backoff was deterministic on both platforms, so an outage that failed
  100 000 installs in the same second produced 100 000 retries in the same second,
  and again at every later attempt. Now spread by equal jitter.
- `HttpRequestWorker` swallowed `CancellationException`, reporting a pre-empted
  task as a failure and re-arming it.
- iOS `SingleTaskExecutor` never called `Worker.close()`, and emitted progress
  keyed by worker class, so two concurrent tasks of the same type were
  indistinguishable and shared one throttle entry.
- An exact alarm that AlarmManager refused threw out of the public `enqueue()` and
  left `AlarmStore` claiming an alarm the system never held.
- `ParallelHttpDownloadWorker` sent `Range: bytes=0--1` for any file smaller than
  `numChunks`.

Plus nine lower-severity fixes; see the commits.

### Unimplemented cancellation no longer fails silently

`BackgroundTaskScheduler.cancelByTag()` and `cancelByWorkerClass()` carry no-op
defaults so that adding them did not break third-party implementations of the
interface. The defaults were *completely* silent, which meant a scheduler that had
never implemented tagging was indistinguishable from one where nothing matched the
tag: the caller believed the work was cancelled, and it kept running.

They still do not throw — that is the point of having a default — but they now emit
one `WARN` naming the implementing class and the member:

```
MyCustomScheduler does not implement cancelByTag() — the call for 'user-123'
cancelled nothing. This is the no-op default on BackgroundTaskScheduler;
override cancelByTag() if this scheduler is expected to support it.
```

The warning fires at most once per member per implementation, so a cancel-in-a-loop
does not flood the log, and two schedulers in one process each get told.

## Internal: `IosFileStorage` split — stages 0b through 4

`IosFileStorage` was a 2,032-line god-class owning seven unrelated responsibilities. It is
now a **796-line façade** delegating to six focused files under `background/data/storage/`.
The split is tracked in `docs/internal/IOS_FILE_STORAGE_SPLIT.md`.

**Nothing about this is visible from the outside.** No public API changed — `apiCheck` is
green — no on-disk format changed, and every public method `IosFileStorage` had, it still
has, as a one-line delegation. If you only consume this library, this section is noise.

| File | Owns |
|---|---|
| `StorageFileIo` | coordination + atomic writes + directory listing (added; not in the plan) |
| `ChainQueueRepository` | both append-only queues, the size cap, the priority sort, `replaceChainAtomic` |
| `ChainDefinitionStore` | chain definitions and the REPLACE deleted markers |
| `ChainProgressStore` | the debounced progress buffer, emergency flush, self-heal |
| `TaskMetadataStore` | task metadata sidecars, the tag/worker scans, the stale reaper |
| `StorageMaintenance` | the disk-space guard and the periodic maintenance run |

It went out as six commits, not one, and the order is not the plan's. Stage 1's premise —
that the progress code was a "tight, self-contained unit" — turned out to be false when
measured, which forced a Stage 0b that the plan never anticipated; and Stage 4 had to precede
Stage 3 because the queue's REPLACE transaction needs the definition store, which needs the
disk-space guard.

Three things the move surfaced that were already wrong in the old code:

- **The lock-ordering invariant was false.** It stated that `progressMutex` was "COMPLETELY
  INDEPENDENT" of `queueMutex` and that no code path held both. `replaceChainAtomic` has
  always held both. The code is safe — nothing takes them in the opposite order, so no cycle
  exists — but a documented rule that production code visibly breaks trains readers to ignore
  the rule. The banner now states the real ordering.
- **`tasksQueueMutex` was dead**, declared when the dynamic-task queue was added and never
  acquired anywhere. Invisible in a 2,000-line file; flagged the moment the code moved.
- **`close()`'s comment named a field that had moved**, and five private helpers in the
  façade had no callers left.

43 new tests across the five stores, reverse-verified: for each one that pins a
cross-cutting invariant, breaking that invariant in the production code was confirmed to turn
the test red (buffer eviction before delete, self-heal dropping progress, maintenance not
recording a failed run, the queue cap, the REPLACE transaction's progress deletion).

The plan's other acceptance criterion — run `QA_PersistenceResilienceTest`,
`QA_IosChainReplaceConcurrencyTest` and `IosStorageStressTest` before merging — is met, but
the third one needed the opt-in flag to mean anything: without `KMP_RUN_STRESS_TESTS=1` its
two tests return in 0.0s and still report as passing. Run with the flag they take 1.5s and
0.13s and pass, alongside `IosDynamicTaskDispatcherTest`'s gated stress case — which matters
here, because concurrency under load is exactly what moving the queue mutexes could have
broken.

**Stage 5 — deleting the façade — is deliberately not done.** `IosFileStorage` is public API,
so removing it needs a major version and a deprecation cycle. This is a hardening release; it
ships no breaking change.

## Documentation corrections

Three public statements were false and have been corrected:

- `docs/COVERAGE.md` claimed `-Xbinary-test-coverage` was enabled (it appears in no
  build file), reported iOS line/branch coverage "via binary instrumentation" (Kover
  cannot instrument Kotlin/Native at all), and gave wrong Kover thresholds. Rewritten,
  with a table recording each removed claim.
- `TaskTrigger.Windowed`'s KDoc — shipped to every consumer's IDE — said iOS logs but
  does not enforce `latest`. It has been enforced since v3.4.0: a task whose window has
  closed is skipped, not run late. What remains true is narrower: iOS chooses the start
  time, so `latest` is a deadline, not a target.
- README said "600+ tests"; the real figure is 1,375.
- `docs/COVERAGE.md` said Kotlin/Native coverage was "planned work, not something already
  done". Trying it showed a stronger result: `-Xbinary-test-coverage` and `-Xcoverage` are
  both rejected — `flag is not supported by this version of the compiler` — by kotlinc-native
  2.1.21, 2.4.0 and 2.4.10 alike. There is no compiler-level coverage instrumentation for
  Kotlin/Native to enable, and upgrading Kotlin would not change that. Recorded as a
  reproducible negative result so the next person does not re-run the experiment.
- `CLAUDE.md` and `docs/internal/IOS_FILE_STORAGE_SPLIT.md` both told contributors to test
  `IosFileStorage` with `DirectCoordinationStrategy()` / `NSFileCoordinationStrategy(...)`.
  Neither type exists, and no `CoordinationStrategy` type ever did. Worse, the path they
  claim to cover is unreachable from a test at all: `IosFileCoordinator.coordinate` ORs its
  flag with `IosTestEnvironment.isTestEnvironment`, so every test in the simulator binary
  takes the skip path. Both documents now say so.

### The publish build was broken by the storage refactor

`compileIosMainKotlinMetadata` — the shared-iOS compilation that only runs when publishing —
failed to resolve `URLByAppendingPathComponent` and `URLByAppendingPathExtension` in the
extracted `StorageFileIo`. The file it was extracted from imports `platform.Foundation.*`;
the extraction listed those two explicitly, which the platform compilations accept and the
metadata compilation does not.

Nothing in the normal loop catches this: `iosSimulatorArm64Test`, `allTests`, `detekt` and
`apiCheck` all pass, because none of them runs the metadata compilation. It surfaces only on
`generateFullMavenZip` — i.e. at publish time. Found by running that task rather than
assuming it still worked, and the Maven bundle now builds with all five modules and all
three iOS targets present.

### Signing keys and refresh tokens were printed by `toString()`

`HmacSigningConfig.secretKey`, `TokenRefreshConfig.refreshBody` and
`TokenRefreshConfig.refreshHeaders` are properties of `data class`es, so the generated
`toString()` printed them in full.

This library never logs a config — that was checked, and `inputJson` never reaches a log
line either. But it does not own the call site. A host writes `Logger.d("scheduling
$config")`, an exception message interpolates the object, or a crash reporter captures it,
and a signing key is in a log aggregator permanently. Both types now redact those fields
while keeping the rest visible, so the value stays debuggable.

The separate fact that these values reach *disk* as part of the persisted task input is
inherent — the task has to survive process death to be retried — and was already documented
on both classes. This closes the other path, which was neither inherent nor documented.

### `close()` could hang forever on a cancelled progress flush

`flushProgressBuffer` publishes a `CompletableDeferred` so concurrent `flushNow()` callers can
await an in-flight flush instead of starting a second one, and completes it in a `finally`.
`Mutex.withLock` suspends when the mutex is contended, and suspending inside a cancelled
coroutine throws — so a flush cancelled while another coroutine held `progressMutex` skipped
both the state reset and the completion. `flushNow()` then read the still-set signal and
awaited it forever. That is `IosFileStorage.close()`, or a chain completing, hanging
permanently.

**The first attempt to reproduce this failed**, across roughly 65 rounds of contention, and it
was nearly shipped as "hardening against a hazard we cannot demonstrate". The reason turned out
to be mundane: every `progressMutex` critical section in that class is pure in-memory work — a
map put, a snapshot, a clear — so the window where the `finally` finds the mutex contended is
microseconds wide, and one or two concurrent savers essentially never land in it.

Fifty savers in tight loops do. With a test hook holding the flush inside its write loop, the
hang reproduces on the **first** round with the fix removed, and all 15 rounds pass with it in
place. The fix is `withContext(NonCancellable)` around that `finally`.

`ProgressFlushDeadlockTest` keeps all three layers: the isolated proof that a contended
`withLock` in a cancelled `finally` throws, the original contention stress case, and the
deterministic reproduction.

### Draining the iOS queue cost quadratic time

`dequeue()` calls `shouldCompact()` on every successful pop, and `shouldCompact()` called
`countTotalLines()`, which walks the queue file record by record. `enqueue()` walked it too,
to compute the new item's index. So both operations were O(N) and filling or draining a queue
was O(N²) — against a documented ceiling of `MAX_QUEUE_SIZE = 10,000`, on a platform where a
BGTask's whole budget can be ~30 seconds.

Measured, not estimated: draining 1,000 items took **2.67 s**, and 4x the items cost **10.9x**
the time. With the record count cached it is **0.65 s** and **4.4x** — the quadratic term is
gone and growth is essentially linear.

The cache is validated against the queue file's size rather than trusted blindly. That
matters because several `AppendOnlyQueue` instances can share one directory
(`NativeTaskScheduler` and `ChainExecutor` do), and `getSize()`'s KDoc already recorded why
the count used to be read from disk every time: a per-instance counter silently diverges from
what another instance wrote. A first version of this cache ignored that, and the existing
suite caught it. Comparing the file size costs one `stat` instead of a full walk, and every
mutation this class performs changes it.

Reverse-verified: removing a single one of the seven cache-invalidation points turns five
tests red, including "Queue must be empty after draining".

### Exact alarms left no trace in execution history

Every other execution path writes an `ExecutionRecord` — `BaseKmpWorker` on Android,
`ChainExecutor` and `SingleTaskExecutor` on iOS. `DefaultAlarmReceiver` did not, so a
`TaskTrigger.Exact` task ran, succeeded or failed, and never appeared in
`getExecutionHistory()`.

Easy to miss, because everything *else* about the run was reported: the completion event
fired, telemetry fired, the log line appeared. Only the durable record a host app shows its
users was absent. Records are now written on every terminal path, including the ones that
never reach the worker — an uninitialised library, an unresolvable worker, a worker that
throws — since those are the runs an operator most needs to see afterwards.

The save is wrapped in `runCatching`, matching `BaseKmpWorker`: history is diagnostic, and
failing to record a run must never fail the run.

### Windowed tasks lost every constraint on their first retry

`scheduleWindowedTask` persisted no constraint metadata — no `requiresNetwork`,
`requiresCharging` or `isHeavyTask`, no `maxRetries`, no standalone-constraint keys. A
Windowed task uses a dedicated Info.plist identifier, so its retry goes through
`reconstructConstraintsFromMetadata`, which read those absent keys as all-false.

The effect: a heavy Windowed task's **first** retry was re-submitted as a
`BGAppRefreshTaskRequest` (~30 s hard ceiling) instead of a `BGProcessingTaskRequest`
(minutes of budget), for that attempt and every attempt after it — and the caller's
`maxRetries` cap was silently replaced by the default.

This is exactly the bug fixed for `scheduleOneTimeTask` in v3.4.0
(`V340OneTimeTaskMetadataFieldsTest`). The Windowed path never got the same fix, and nothing
covered it. Found by a new test written to close an internal issue about an unrelated
hand-maintained list.

### Dot-prefixed ids were invisible to every iOS listing

A task or chain whose id starts with `.` was stored, readable by id, and absent from every
listing. `listJsonFileIds` enumerated with `NSDirectoryEnumerationSkipsHiddenFiles`, and the
path encoder deliberately leaves a leading dot alone — so `.internal.sync` became
`.internal.sync.json`, which the OS calls hidden.

Nothing looked broken from outside: `loadTaskMetadata(id)` returned the record. What broke
was `queryTasks`, `computeIosTaskState`, and the catch-up scan for missed exact alarms.
`findTaskIdsByWorkerOrTag` enumerates differently and always saw those ids, so `cancelByTag`
and `queryTasks` disagreed about which tasks existed — a task could be cancellable but
unlistable.

Found by a new security test, not by review.

## Tests

Four groups of tests were not running, and three of the four stated reasons were
wrong. The KSP compile-testing suite (23 tests) had never executed since it was
written — the harness used a deprecated setter that drives kctfork's KSP1 path
while the processor targets KSP2. Turning it on found a defect in the generated
iOS factory's KDoc.

`EventPersistenceIntegrationTest` was ignored for a reason that no longer applied
and was hiding four real defects. The two load-sensitive iOS stress tests moved
from `@Ignore` to an opt-in flag that announces itself when it skips
(`KMP_RUN_STRESS_TESTS=1`).

**The suite now has 0 skipped tests, down from 29.**

### New coverage in this release

Kover was used to find classes with no test at all, rather than guessing where the gaps were.
Three had none in any source set:

- **`FileCompressionWorker` (Android)** — 14 tests. The README calls it Stable and claims a
  real PKZIP archive; nothing verified that on Android, while the iOS actual had its own
  test file. The new tests read output back with `java.util.zip.ZipFile` instead of trusting
  the worker's success message, and cover both path-traversal rejections plus a zip-slip
  guard on entry names.
- **`HttpSyncConfig`, `IosBackgroundDownloadConfig`, `IosBackgroundUploadConfig`** — 13
  tests. These are the library's public input surface, serialised by a host and deserialised
  by a worker across a process boundary, so their `init` blocks are the only thing between a
  caller's typo and a silent background failure. Each is pinned twice: `require` rejects at
  construction, and a valid config survives a JSON round-trip — the `init` block runs again
  on decode, so a rule stricter than the serialiser can produce would make a config writable
  but not readable on the next launch.
- **The extracted storage layer** — 5 security tests and 6 performance/stress tests. Ids are
  caller-supplied and every store interpolates them into a filename, so the security tests
  assert on the filesystem rather than on the encoder's output: nothing lands outside the
  store's directory, ids differing only in escaped characters do not share a file, and
  `.`/`..` round-trip as distinct files. **These found the dot-prefix bug above.** The
  performance tests pin scale-relative ratios rather than wall-clock absolutes.

Measured `kmpworker` line coverage moved from 69.4% to **73.3%**, and the CI floor was raised
from 62% to 70% to match — a floor left far below the real figure stops being a ratchet.

**Total: 2,646 test runs, 0 failures, 0 errors, 0 skipped** — 1,473 distinct tests across
seven source sets, several of which run on more than one target.

> **Note on `./gradlew :kmpworker:allTests`.** On Apple Silicon the Kotlin plugin disables
> `iosX64Test` (there is no x64 simulator to run it on), but `allTests` still tries to
> aggregate a report from that target's binary results and fails deserializing them
> (`EOFException` / Kryo "Buffer underflow"). The build goes red on a clean checkout even
> though every test passed. It is a Gradle/KMP aggregation limitation, not a test failure —
> the per-target XML under `build/test-results/` shows the real outcome. CI is unaffected
> because it runs the concrete test tasks in their own jobs. `CLAUDE.md` now points
> contributors at those tasks instead.

## Demo app

Both demos were built and run for this release rather than assumed to work: the Android app
on a physical device and the iOS app on a simulator. Scenarios exercised end to end —
one-time tasks, sequential and parallel chains, `InputMerger`, and the constraint demos —
produced no library-level WARN or ERROR.

Running it on a physical iPhone surfaced a third defect, this one iOS-only and reported by
the user within seconds of tapping: after tapping one scenario, every other button on the
Demo Scenarios screen stayed disabled for the rest of the session.

`isAnyTaskRunning` was cleared **only** by a `TaskEventBus` completion event. On Android
WorkManager starts the work within seconds, the event arrives, and the screen frees up — so
it looked correct. On iOS `enqueue()` hands a `BGTaskRequest` to the OS, which decides when
to run it; for an app sitting in the foreground that is essentially never, so the event never
came and the flag never cleared. The only escape was a "Stop" button that just reset the flag.

The flag now clears when the enqueue call returns, in a `finally`, because scheduling is what
the button actually does. The indicator also said "Task Running" while nothing was running —
it now says "Scheduling", which is true on both platforms.

That run surfaced two defects in the demo's own dashboard, both now fixed. Durations always
read `0ms`, because the dashboard subscribed to `TaskEventBus` (whose `TaskCompletionEvent`
carries no duration) and dug for an optional `outputData["duration"]` almost no worker sets —
while `TelemetryHook.TaskCompletedEvent.durationMs` had the real figure all along. And every
task counted twice, because that bus carries both the library's completion event and the
demo's own snackbar event, which are indistinguishable after `substringAfterLast('.')`.
Sixteen demo runs reported as 16 tasks with 8 real executions behind them; one run now
reports as one, at 2s against telemetry's 2417ms.

These were demo-only defects — the library's own persisted records were never affected — but
the demo is what a new user runs first.
